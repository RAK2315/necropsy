# Requirements Document

## Introduction

NECROPSY's renderer (`web/pixels.py`, `web/serialise.py`) turns a resolved candidate into a picture. Three cases draw a picture that does not match what the file declares, or draw nothing although the file declares enough to draw it. This spec fixes those three cases and adds the one payload item 4, and nothing else.

1. **Palette TIFF.** `libtiff_palette-1c-8b.tiff` and `goimage_video-001-paletted.tiff` declare PhotometricInterpretation 3 and a ColorMap (tag 320). Their decoded indices already equal Pillow's, but the picture is grey because nothing reads the ColorMap. The TIFF probe reads tag 320 as a declared field, in the same category as tag 262 (structure-inference-engine Decision Record item 23), and the renderer draws the indices through it.
2. **16-bit TGA.** `pillow_200x32_la_bl_raw.tga`, `pillow_la.tga` and `pillow_rgba16.tga` resolve, and the renderer answers `no renderer for 16-bit pixels`. The file declares the pixel layout (image type, bit depth, and the alpha-bit count in the image descriptor), so the renderer draws them.
3. **Sub-byte samples with several channels.** A TIFF whose BitsPerSample is below 8 and whose SamplesPerPixel is above 1 can resolve, and the renderer draws it as one grey sample. That is a wrong picture. The renderer shows no picture and states why. This case was found on the sealed evaluation set. The set is not used for development or measurement; the fixture is built in code from a documented byte layout. It is fixed anyway because showing a wrong picture is the one thing NECROPSY must never do.
4. **Which reading a rejection is.** This item is not one of the three cases. It is a payload addition requested alongside them (Requirement 11). Each serialised rejection of a hypothesis whose trailer matched names its reading and the trailer. It changes no picture and no status.

Settled decision 1 governs all three: read what the file declares, never encode knowledge the file does not state. The renderer follows the file's declarations and never re-implements inference. Coding locks 30 Nov 2026.

## Glossary

- **Engine**: The Structure-Inference Engine (`Engine.run`). Its inference does not change in this spec: status, termination, candidates, hypothesis keys, check counts and rejection order stay as they are. The one addition is Requirement 11: `RejectionEntry` carries two more recorded values.
- **TIFF_Probe**: `probe_tiff` in `necropsy/engine/probes.py`.
- **TGA_Probe**: `probe_tga` in `necropsy/engine/probes.py`.
- **Renderer**: `decode` in `web/pixels.py`, with the helpers in `web/serialise.py` that read a candidate's `FieldRecord`s and pass declared values to `decode`.
- **Serialiser**: `web/serialise.py`.
- **Candidate**: A hypothesis that passed closure, as defined by the Engine.
- **FieldRecord**: A field read from the bytes: name, byte offset, `struct` format string, and the tuple returned by `struct.unpack_from`, never unwrapped.
- **ColorMap**: TIFF tag 320. Type SHORT (3), count `3 × 2^BitsPerSample`. The values are all reds, then all greens, then all blues, each a 16-bit word in the byte order of the TIFF header.
- **Map_Size**: `2^BitsPerSample`, the number of entries per colour in a ColorMap.
- **IFD_Entry**: A 12-byte TIFF directory entry. Tag at entry + 0 (`H`), type at entry + 2 (`H`), count at entry + 4 (`I`), value field at entry + 8 (4 bytes), all in the header's byte order.
- **Array_Rule**: The rule the TIFF_Probe uses for arrays (`_read_range_array`). If `count × bytes_per_value > 4`, the value field holds an `I` offset and the values start there. Otherwise the values start at entry + 8.
- **Palette_TIFF**: A candidate with probe `tiff` whose recorded `photometric_interpretation` is 3.
- **Image_Descriptor**: TGA byte 0x11, recorded as field `image_descriptor`. Bits 0 to 3 are the alpha-bit count. Bit 5 is the row origin (already read by Decision Record item 14).
- **Alpha_Bits**: `image_descriptor & 0x0F`.
- **TGA_Word**: One 16-bit TGA pixel, read as `<H`.
- **Attribute_Bit**: Bit 15 of a TGA_Word of a 16-bit colour pixel.
- **Expand5**: The 5-bit to 8-bit scaling `v * 255 // 31`, already used by `_expand5` for TGA colour-map entries.
- **Scale16**: The 16-bit to 8-bit ColorMap scaling `v >> 8`.
- **PixelBuffer**: The renderer's success value (`grey8` or `rgb8` data plus a note).
- **RenderFailure**: The renderer's error value. Its reason is shown to the user in place of a picture.
- **Pillow_Render**: `Image.open(...).convert("RGB").tobytes()`, the comparison used by `tests/ui/test_render_vs_pillow.py`.
- **Real_Corpus**: The files in `spike/samples/real/`. **Samples**: every file under `spike/samples/`, whether directly in it or in any folder below it (including `spike/samples/real/` and `spike/samples/external/`), except the Sealed_Set. Samples and Real_Corpus are the only sets used to develop and measure this work.
- **Sealed_Set**: The sealed evaluation set. It is the one folder under `spike/samples/` that Samples excludes. It is never read, listed, named or tested against, and no path to it is written anywhere.
- **Requirement_12_Check**: The check that header fields and pixel data are disjoint (Decision Record item 17).
- **Reading**: One data end checked for a hypothesis (Decision Record item 24). A hypothesis with no declared `data_end` whose trailer matches the trailer registry has two readings: the Trailer_Reading and the EOF_Reading.
- **Trailer_Reading**: The Reading whose data region ends at the trailer's start. It is the hypothesis as the probe or revision strategy produced it, with `data_end` of `None`.
- **EOF_Reading**: The Reading whose data region runs to the end of the file. It is the same hypothesis with `data_end` replaced by the file length (`readings` in `necropsy/engine/closure.py`).
- **Trailer_Name**: The `name` of the matched `TrailerEntry` in `necropsy/engine/trailers.py` (`pcx_palette_256` or `tga2_footer`).
- **RejectionEntry**: The Engine's record of one rejected hypothesis (`necropsy/engine/types.py`): `reason`, `source`, `hypothesis`, `discrepancy`, `detail`.
- **Rejection_Item**: One element of the `rejections` list of the web payload, built by `_rejection` in `web/serialise.py`.
- **Web_Payload**: The dict returned by `to_payload` in `web/serialise.py`.
- **MCP_Analyse**: The output of the `analyse` tool of `necropsy_mcp/`, which is the Web_Payload with exactly three things removed (`spec`, each candidate's `render.data_b64`, and `value_repr` from every field).

## Decisions

These are made before any code, each with its reason and the measurement behind it.

1. **ColorMap is one FieldRecord with an array format.** Name `color_map`, offset the first value, format `<Nh`-style `order + f"{N}H"`, value the unwrapped tuple of N integers. One record, not N, so the record list, the payload and any emitted text stay small, and the `FieldRecord` rule "the tuple returned by `struct.unpack_from`, never unwrapped" holds. ColorMap is one field, never a rejection and never a status change. Decided by Claude Code on Rehaan's delegation, 27 Nov 2026.
2. **The probe reads at most 768 values and never rejects for tag 320.** 768 is `3 × 2^8`, the largest ColorMap the renderer can use (BitsPerSample 8). A ColorMap that is absent, of another type, larger than 768 values, or partly outside the file is recorded as absent. It adds no rejection, so no status changes. The reason a picture is missing is stated by the Renderer (Requirement 3). Decided by Claude Code on Rehaan's delegation, 27 Nov 2026 (together with Decision 1).
3. **Scale16 is `v >> 8`.** Measured on the Real_Corpus against Pillow's palette: `v >> 8` equals Pillow's palette for all 768 entries of both palette files. `v * 255 // 65535` equals Pillow's for `goimage_video-001-paletted.tiff` and differs for `libtiff_palette-1c-8b.tiff`. Pillow is the comparison; `v >> 8` is chosen because it matches on both. If a later measurement differs, the result is recorded as measured and the rule is not adjusted to make a result clean. Approved: decided by Claude Code on Rehaan's delegation, 27 Nov 2026.
4. **Expand5 is `v * 255 // 31`.** Measured on `pillow_rgba16.tga`: the three colour values of pixel 1 (5-bit 21, 0, 31) give 172, 0, 255, and of pixel 2 (0, 31, 10) give 0, 255, 82. Both equal Pillow's RGB.
5. **Alpha is not drawn.** The existing renderer produces only `grey8` and `rgb8` buffers, and for 32-bit pixels it ignores the fourth byte and says so in its note. The new TGA renders follow that convention: the alpha channel is ignored and the note says so. The Attribute_Bit polarity (set means opaque or set means transparent) is not declared by the Image_Descriptor, and Pillow reads set as transparent on `pillow_rgba16.tga`. Because no alpha is drawn, the picture does not depend on polarity and the renderer states none.
6. **The alpha-bit count decides whether the 16-bit layout is readable.** For colour types the five-five-five colour bits are fixed by the word layout, so the count only changes what the note says. For grey types the count decides which bits are grey: the file declares 16 bits per pixel and Alpha_Bits of them as alpha, and the remaining `16 − Alpha_Bits` low bits are the grey sample. The renderer draws grey only when that remainder is 8: 16 − 8 = 8 grey bits, derived from the file's own counts, and the grey sample is the low byte of the TGA_Word. Otherwise the renderer shows no picture and states the reason (Requirement 5.3). Decided by Claude Code on Rehaan's delegation, 27 Nov 2026.
7. **`pillow_rgba16.tga` declares an alpha-bit count of 8 on a five-five-five pixel.** Its descriptor is 0x08 (measured). A 16-bit colour pixel has one bit left after the colour bits, so a declared count of 8 describes more alpha bits than the pixel has. The renderer draws the colour from the five-five-five layout that the image type and the bit depth declare, ignores alpha, and states in the note that the descriptor "declares 8 alpha bits, which the 16-bit pixel cannot hold". No picture was rejected as the alternative, because the colour layout itself is fully declared by the image type and the bit depth, and only the alpha count is inconsistent. Decided by Claude Code on Rehaan's delegation, 27 Nov 2026. The 2-of-8 canonical mismatch recorded by `tools/real_corpus.py` compares decoded words, not the picture, and does not change (Requirement 8.4).
8. **Palette rendering is limited to 8 bits per sample.** The two palette files and the invalid one are all BitsPerSample 8. A Palette_TIFF at another BitsPerSample would today be drawn as grey, a wrong picture. The renderer answers with a RenderFailure instead (Requirement 3.4). A 1-bit, 2-bit or 4-bit palette renderer is not requested and is not built.
9. **The picture for sub-byte multi-channel samples is no picture.** The simpler of the two options in the request. Drawing per channel needs bit-unpacking of each channel for every depth and layout; refusing needs one condition and one reason string.
10. **`goimage_invalid-palette-ref.tiff` changes from a grey picture to no picture.** Measured: it is a Palette_TIFF (tag 262 = 3) that resolves, with tag 320 declaring count 195 at offset 37 where 768 is required for BitsPerSample 8, and Pillow refuses the file. Its grey picture was wrong in the same way as the two palette files. Its new picture is no picture with both counts stated (195 found, 768 required). It cannot be compared with Pillow. Approved: decided by Claude Code on Rehaan's delegation, 27 Nov 2026.
11. **Measured scope, from the survey of Samples and Real_Corpus resolved files.** Resolved Palette_TIFFs: 3 (the files above). Resolved 16-bit TGAs: 3 (the files above). Resolved TIFFs with BitsPerSample below 8 and SamplesPerPixel above 1: 0. The case 3 fixture is therefore built in code (Requirement 9.3). A resolved TIFF with BitsPerSample 8 and SamplesPerPixel 2 was looked for and none exists, so it is not in scope. It would share the 16-bit grey path and is noted here as an observation, not a requirement. Requirement 11 (the rejection reading) is outside this survey because it changes no picture and no status: it adds keys to rejection items only.
12. **The rejection reading is two flat keys, `reading` and `trailer`, recorded by the Engine.** Measured on the code (27 Nov 2026):
    - Decision Record item 24 is implemented by `readings` in `necropsy/engine/closure.py`. A hypothesis with `data_end` of `None` whose trailer matches becomes two hypotheses: itself (the Trailer_Reading, `data_end` `None`) and a copy with `data_end` replaced by the file length (the EOF_Reading). The Engine checks both and appends a `RejectionEntry` for each that fails, in `Engine._run`, `Engine._revise` and (for Generic Search) the `on_reject` closure of `Engine._generic`.
    - `RejectionEntry` holds `reason`, `source`, `hypothesis`, `discrepancy` and `detail`. It holds no reading and no trailer name. `ClosureVerdict.trailer` is set only when the closure check accepts; on a rejection it is `None` (`_reject` in `closure.py`).
    - The Hypothesis inside a rejection does differ between the two readings (`data_end` `None` against the file length, serialised as `declared_data_end`), but that is not enough to name the reading. A TIFF hypothesis also has a `data_end` that is not `None`, and the Serialiser cannot tell a trailer-matched hypothesis from an unmatched one without reading the trailer registry, which would be inference in the Serialiser. The trailer name is nowhere in the record.
    - The minimal recorded value needed is therefore two optional fields on `RejectionEntry`, `reading` and `trailer`, both `None` by default, set by the Engine at the three places it creates a rejection for a hypothesis, from the information the Engine already holds when it makes the readings. No inference, status, key or candidate changes, because the new values are written after the closure check and nothing reads them.
    - Key names. The Web_Payload already has a `trailer` key on candidates (the matched trailer's name, `null` for a candidate that closed at the end of the file). The rejection key uses the same name `trailer` for the same registry name, but on a rejection it is present for both readings, because the request is for the trailer's name beside the reading. The difference is stated in Requirement 11.6.
    - One field was considered: `reading` as an object with `kind` and `trailer`. Two flat keys are chosen because every other rejection key is flat, a viewer can show `reading` alone, and a script reads one key each. The object form would be the only nested value in a rejection item.
    - A rejection with no hypothesis (the Generic Search trailer error, `hypothesis` `null`) carries neither key. It is a trailer rejection by construction, so a reading label adds nothing, and recording it would change `on_reject`'s two-argument signature, which `tests/test_generic.py` passes as a two-argument callable.
    Decided by Claude Code on Rehaan's delegation, 27 Nov 2026.

13. **The emitter describes `color_map` and does not print its values.** The emitter prints field values in two places: the structure table and the emitted test's field list. With Requirement 1, three Real_Corpus files carry a `color_map` field (`libtiff_palette-1c-8b.tiff`, `goimage_video-001-paletted.tiff`, `goimage_invalid-palette-ref.tiff`), and printing up to 768 values in each place would bloat the emitted spec. Both places describe `color_map` by its tag (320), type (SHORT), count, offset, and the statement that it holds 3 × 2^BitsPerSample values. Only those three emitted specs change, and only by that description (Requirement 8.10 to 8.12). Approved: decided by Claude Code on Rehaan's delegation, 27 Nov 2026.
14. **Two more palette refusals.** (a) A Palette_TIFF at BitsPerSample 8 with SamplesPerPixel above 1 is not a single-index-per-pixel picture, so the renderer refuses it and states SamplesPerPixel (Requirement 3.10). (b) A ColorMap value outside 0 to 65535 is not a 16-bit word, so Scale16 would give a value outside 0 to 255; the renderer refuses it and states the position and the value (Requirement 3.11). The TIFF_Probe reads `H` words, so (b) cannot occur from a probe-built record; it guards `decode` for arbitrary arguments. Both give no picture with the reason stated, never a wrong picture. Decided by Claude Code on Rehaan's delegation, 27 Nov 2026.
15. **Each expectation changes in the commit that makes it wrong.** An expectation is not changed in a separate later task, because the commit that makes it wrong would then leave the suite red. Each expectation changes in the same task and commit as the change that makes it wrong, and the commit message cites the requirement number. Every commit stays green (Requirements 9.1, 9.2, 11.13, 11.16). Decided by Claude Code on Rehaan's delegation, 27 Nov 2026.
16. **Payload size is accepted.** The `color_map` field adds one field entry per palette file, and the Web_Payload carries it (Requirement 7.6). The 30,000-character limit asserted in `tests/test_mcp_server.py` must still pass for the three files that carry it, and the measured MCP_Analyse sizes are reported (Requirement 8.13). `public/` is not edited. A compact on-screen display of `color_map` is later work by Claude Code and is out of scope. Decided by Claude Code on Rehaan's delegation, 27 Nov 2026.
17. **Every folder of `spike/samples/` except the Sealed_Set is measurable.** Samples now includes `spike/samples/external/`. The only forbidden folder is the Sealed_Set, which is never named by path (Requirements 12.4, 12.5). Measured 27 Nov 2026 on `external_a` (a PCX, 1162 bytes) and `external_b` (a TGA, 9260 bytes): neither is a Palette_TIFF, a 16-bit TGA or a TIFF with sub-byte samples, so no render outcome of either changes (Requirement 8.7). Their payload hashes under Requirement 11 are stated in Requirement 11.16. Decided by Claude Code on Rehaan's delegation, 27 Nov 2026.
18. **Requirement 3.3 is tested through a helper with a smaller map size.** The index check compares each pixel index with Map_Size. At BitsPerSample 8 the map size is 256, and every byte index is below 256, so criterion 3.3 cannot be reached through `decode` with real 8-bit data. A test helper that applies the same index check to a smaller map size (for example 4) exercises the branch, and the first-index rule and the reason content are asserted through it. Decided by Claude Code on Rehaan's delegation, 27 Nov 2026.
19. **Palette bit depth must equal 8 × SamplesPerPixel.** A Palette_TIFF at BitsPerSample 8 with no SamplesPerPixel recorded, or with a bit depth (the candidate's bit depth passed to `decode`, the hypothesis bit depth) other than 8 × SamplesPerPixel, is refused with a RenderFailure that states the bit depth and the SamplesPerPixel (or that it was not recorded) (Requirement 3.13). No file in Samples or Real_Corpus reaches it (the three palette files record SamplesPerPixel 1), so no render outcome changes. It is added so that a wrong picture is impossible even for inputs no real file reaches today. It sits after criterion 10 and before criterion 1 in the check order of 3.8 (4, 10, 13, 1, 2, 11, 3). It is tested with a fixture built in code and by calling `decode` directly. Decided by Claude Code on Rehaan's delegation, 27 Nov 2026.
20. **Emitted-spec diff for the three palette files is exactly the color_map description, its criterion line and its layout entry.** Requirement 8.11 states this explicitly, with none of them containing the ColorMap values, and keeps it as the expected diff. Decided by Claude Code on Rehaan's delegation, 27 Nov 2026.

## Requirements

### Requirement 1: TIFF probe reads the ColorMap as a declared field

**User Story:** As a user, I want the TIFF probe to record the ColorMap a file declares, so that the renderer can draw palette indices in the file's own colours.

#### Acceptance Criteria

1. WHEN the TIFF_Probe reads an IFD_Entry whose tag is 320, whose type is 3 and whose count N satisfies `1 ≤ N ≤ 768`, and whose values lie wholly inside the data, THE TIFF_Probe SHALL record one FieldRecord named `color_map` with format `order + f"{N}H"`, where `order` is `<` for a header of `II` and `>` for a header of `MM`.
2. THE TIFF_Probe SHALL locate the values of tag 320 by the Array_Rule with 2 bytes per SHORT value, and SHALL set the FieldRecord offset to the offset of the first value. WHERE `N × 2 ≤ 4`, the offset SHALL be the entry offset + 8. WHERE `N × 2 > 4`, the offset SHALL be the `I` value read at entry + 8.
3. THE TIFF_Probe SHALL unpack the `color_map` FieldRecord with `struct.unpack_from` and SHALL keep the returned tuple of N integers, each in the range 0 to 65535, as its value, unwrapped.
4. IF an IFD_Entry for tag 320 has a type other than 3, a count below 1 or above 768, or any of its `N × 2` value bytes at an offset at or beyond the length of the data, THEN THE TIFF_Probe SHALL record no `color_map` field and SHALL add no rejection for that entry. The probe's rejections, status and other FieldRecords SHALL equal those it produces for the same file with that entry removed from consideration.
5. IF the IFD holds more than one IFD_Entry for tag 320, THEN THE TIFF_Probe SHALL read only the first in directory order, and SHALL record no `color_map` field if that first entry fails criterion 4, even when a later entry for tag 320 is valid.
6. THE TIFF_Probe SHALL keep the `color_map` field out of the seed, the closure arithmetic, the Hypothesis key and the Requirement_12_Check. For every file in Samples and Real_Corpus, the seed, the closure result, each Hypothesis key and the Requirement_12_Check result SHALL be identical whether or not the `color_map` FieldRecord is present in the field list.
7. WHEN a TIFF file declares no tag 320, THE TIFF_Probe SHALL produce a field list identical in names, offsets, formats and values, and in order, to the list produced by the commit immediately before this change.
8. WHEN `Engine.run` is applied to any file in Samples or Real_Corpus, THE Engine SHALL return the same status, termination, candidate set and Hypothesis keys as it returned at the commit immediately before this change.
9. FOR ALL byte sequences of length 0 to 4096, THE TIFF_Probe color-map reading function SHALL return either no FieldRecord or exactly one FieldRecord, without raising. Every FieldRecord it returns SHALL have a value equal to `struct.unpack_from(fmt, data, offset)` of the same data (never-raises and round-trip properties, checked by Hypothesis tests).

### Requirement 2: Renderer draws a palette TIFF through its ColorMap

**User Story:** As a user, I want a palette TIFF shown in the colours the file declares, so that the picture on screen matches the file.

#### Acceptance Criteria

1. WHEN a Palette_TIFF candidate has a recorded `bits_per_sample` of 8 and a recorded `color_map` of exactly 768 values, THE Renderer SHALL return an `rgb8` PixelBuffer with one pixel per index of the decoded raster, in which each pixel with index `i` (0 ≤ `i` ≤ 255) is `(Scale16(map[i]), Scale16(map[256 + i]), Scale16(map[512 + i]))`, where `map` is the recorded `color_map` tuple.
2. THE Renderer SHALL read the reds from `color_map[0:256]`, the greens from `color_map[256:512]` and the blues from `color_map[512:768]`, each value taken as the 16-bit word (0 to 65535) the FieldRecord holds.
3. THE Renderer SHALL compute Scale16 as `v >> 8`, giving an integer from 0 to 255.
4. THE Renderer SHALL state in the PixelBuffer note that the colours come from the TIFF ColorMap (tag 320), the entry count (768), and the 16-to-8-bit rule (`v >> 8`).
5. WHEN a Palette_TIFF candidate is rendered, THE Serialiser SHALL pass the `color_map` value from the candidate's FieldRecords to `decode`, and THE Renderer SHALL NOT read tag 320 or any other TIFF tag from the file bytes itself.
6. FOR ALL ColorMaps of 768 words in the range 0 to 65535 and ALL index rasters of 1 to 4096 pixels with indices 0 to 255, THE rendered `rgb8` data SHALL equal the per-pixel definition in 2.1, byte for byte and with a length of 3 × the pixel count (exact-pixel property, fixture built in code).
7. WHEN `libtiff_palette-1c-8b.tiff` and `goimage_video-001-paletted.tiff` from `spike/samples/real/` are rendered, THE Serialiser payload SHALL carry an `rgb8` render, and its bytes SHALL be compared with Pillow_Render in Requirement 8.3.

### Requirement 3: Renderer says why a palette TIFF has no picture

**User Story:** As a user, I want a palette TIFF that cannot be drawn faithfully to show a stated reason, so that I never see indices drawn as grey.

#### Acceptance Criteria

1. IF a Palette_TIFF candidate has a recorded `bits_per_sample` of 8 and no recorded `color_map`, THEN THE Renderer SHALL return a RenderFailure and no PixelBuffer, whose reason contains the words `palette TIFF` and states that no ColorMap (tag 320) was read.
2. IF a Palette_TIFF candidate has a recorded `bits_per_sample` of 8 and a recorded `color_map` whose count is not 768, THEN THE Renderer SHALL return a RenderFailure and no PixelBuffer, whose reason states the count found as a decimal integer and the count required (768, which is `3 × 2^BitsPerSample` at BitsPerSample 8).
3. IF a Palette_TIFF candidate has a recorded `bits_per_sample` of 8, a recorded `color_map` of 768 values, and at least one pixel index at or above Map_Size (256), THEN THE Renderer SHALL return a RenderFailure and no PixelBuffer, whose reason states the value of the first such index in raster order and Map_Size as decimal integers. THE tests for this criterion SHALL reach it through a helper that applies the same index check with a smaller Map_Size (for example 4), because at BitsPerSample 8 every byte index is below 256 (Decision 18).
4. IF a Palette_TIFF candidate has a recorded `bits_per_sample` other than 8, or no recorded `bits_per_sample`, THEN THE Renderer SHALL return a RenderFailure and no PixelBuffer, whose reason begins `no renderer for palette TIFF` and states the BitsPerSample as a decimal integer, or states that it was not recorded.
5. THE Renderer SHALL NOT return a `grey8` PixelBuffer for any Palette_TIFF candidate.
6. WHEN `goimage_invalid-palette-ref.tiff` is rendered, THE Renderer SHALL return a RenderFailure and no PixelBuffer, whose reason contains the decimal integers `195` and `768` as the ColorMap count found and the count required.
7. FOR ALL inputs to `decode` with `photometric` 3, including any `bits_per_sample` from 0 to 65535, any `samples_per_pixel` (including `None`), any `color_map` of 0 to 1024 values of any integer, and any `decoded` bytes of 0 to 65536 bytes, THE Renderer SHALL return either a PixelBuffer or a RenderFailure and SHALL NOT raise (never-raises property).
8. WHEN a Palette_TIFF candidate fails more than one of criteria 1 to 4, 10, 11 and 13, THE Renderer SHALL report the first failure in this order only: criterion 4, then 10, then 13, then 1, then 2, then 11, then 3.
9. WHEN a Palette_TIFF candidate returns a RenderFailure under criteria 1 to 4, 10, 11 or 13, THE Serialiser SHALL carry the RenderFailure reason in the payload in place of a picture and SHALL carry no `grey8` or `rgb8` render for that candidate.
10. IF a Palette_TIFF candidate has a recorded `bits_per_sample` of 8 and a recorded `samples_per_pixel` above 1, THEN THE Renderer SHALL return a RenderFailure and no PixelBuffer, whose reason begins `no renderer for palette TIFF with SamplesPerPixel` and states the SamplesPerPixel as a decimal integer.
11. IF a Palette_TIFF candidate has a recorded `bits_per_sample` of 8 and a recorded `color_map` of 768 values in which at least one value is below 0 or above 65535, THEN THE Renderer SHALL return a RenderFailure and no PixelBuffer, whose reason states the position (zero-based, in `color_map` order) and the value of the first such entry as decimal integers, and the range 0 to 65535.
12. THE refusals of criteria 10, 11 and 13 SHALL give no picture with the reason stated, and SHALL NOT return a `grey8` or `rgb8` PixelBuffer for the candidate (Decisions 14 and 19).
13. IF a Palette_TIFF candidate has a recorded `bits_per_sample` of 8 and either no recorded `samples_per_pixel`, or a bit depth (the candidate's bit depth passed to `decode`) not equal to `8 × SamplesPerPixel`, THEN THE Renderer SHALL return a RenderFailure and no PixelBuffer, whose reason states the bit depth as a decimal integer and the SamplesPerPixel as a decimal integer, or states that SamplesPerPixel was not recorded. A SamplesPerPixel above 1 is refused first by criterion 10, so criterion 13 is reached with a SamplesPerPixel of 0 or 1 or none, or with a negative value (Decision 19). THE criterion SHALL be tested with a fixture built in code and by calling `decode` directly, including bit depth 16 with SamplesPerPixel 1 and bit depth 8 with no SamplesPerPixel. No file in Samples or Real_Corpus reaches this refusal (the three Real_Corpus palette files each record SamplesPerPixel 1 at BitsPerSample 8, measured 27 Nov 2026, so 2.7 and 3.6 are unaffected).

### Requirement 4: Renderer draws 16-bit TGA colour pixels

**User Story:** As a user, I want a 16-bit colour TGA shown in its colours, so that the picture matches the file.

#### Acceptance Criteria

1. WHEN a TGA candidate has image type 2 or 10 and bit depth 16, THE Renderer SHALL read each pixel as a TGA_Word (`<H`, byte 0 low) and SHALL return an `rgb8` PixelBuffer with red `Expand5((w >> 10) & 31)`, green `Expand5((w >> 5) & 31)` and blue `Expand5(w & 31)`, where Expand5 is `v * 255 // 31`.
2. THE Renderer SHALL ignore the Attribute_Bit (bit 15) and SHALL state in the note that alpha is not drawn.
3. WHEN Alpha_Bits is 0, THE Renderer SHALL state in the note that the descriptor declares no alpha bits.
4. WHEN Alpha_Bits is 1, THE Renderer SHALL state in the note that bit 15 is declared as alpha and is not drawn.
5. ### Requirement 5: Renderer draws 16-bit TGA grey pixels
